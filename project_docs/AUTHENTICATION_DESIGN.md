# Authentication and Conversation Isolation Design

## Decision

Do not expose the current API as a multi-user public service yet. The present application stores all conversations in one JSON document and its conversation routes do not authenticate callers. Adding a shared static token to browser JavaScript would not solve this: every visitor could extract it.

This document records a safer implementation direction before changing the application contract.

## Recommended first production architecture

For a portfolio demo with a small number of invited users:

1. Put the API behind an identity-aware reverse proxy or managed authentication gateway.
2. Require the gateway to validate each user's login and pass a verified, immutable user identifier to the application through a protected upstream header.
3. Configure the application to accept that identity header only when direct public access to the application service is blocked and only the trusted gateway can reach it.
4. Derive the user identity on the server for every request. Never accept an owner/user ID from request JSON, query parameters, or browser storage as proof of identity.
5. Scope every conversation lookup, list, update, and delete operation by the authenticated user identifier.
6. Migrate the flat JSON history file to a transactional store with a schema that includes an owner ID. Do not use a conversation UUID as a substitute for authorization.

A gateway that merely injects a header while leaving the application directly reachable is not a secure implementation.

## Data model

A future persistent conversation record should include:

- `conversation_id`: unguessable UUID generated by the server.
- `owner_id`: stable subject identifier from the verified identity provider.
- `title`, `created_at`, and `updated_at`.
- `messages`: ordered records with role, content, timestamp, and source metadata.

Required database constraints and query rules:

- Every read/update/delete includes both `conversation_id` and `owner_id`.
- Listing filters by `owner_id` before pagination.
- A request for another user's conversation returns 404, not its contents.
- User deletion and retention policy are explicit and tested.
- Database credentials are server-side secrets with least-privilege access.

## API contract changes

The browser must not send an owner ID. The server obtains it from the verified request identity.

| Route | Required behavior |
|---|---|
| `GET /api/conversations` | Return only the caller's conversations |
| `GET /api/conversations/{id}` | Return only if owned by caller; otherwise 404 |
| `DELETE /api/conversations/{id}` | Delete only if owned by caller |
| `PUT /api/conversations/{id}/title` | Rename only if owned by caller |
| `POST /api/query` | Save and stream only within caller's conversation scope |

The status endpoint may remain public only if it reveals no secrets, internal paths, provider configuration, or sensitive operational details.

## Alternative for a single-user private demo

If the application is strictly private and only one trusted operator uses it, a server-side bearer token can protect API routes. The token must be stored in the host's secret manager and supplied by a trusted client, never embedded in `app.html`. This is not a multi-user identity system and should not be presented as one.

## Security tests required before release

- Unauthenticated requests to protected routes are rejected.
- User A cannot list, read, rename, or delete User B's conversations.
- A caller cannot change ownership by submitting an `owner_id` field.
- Random conversation IDs do not grant access.
- Direct access that bypasses the trusted identity gateway is blocked.
- Expired/revoked sessions are rejected.
- Query rate limits and maximum request sizes are enforced.
- Security tests run in CI alongside retrieval metric tests.

## Rollout sequence

1. Choose the identity provider/gateway and confirm it can protect the Railway service end-to-end.
2. Block direct access to the app service except through that gateway.
3. Implement server-side identity extraction and authorization dependency.
4. Migrate conversation storage to owner-scoped records.
5. Update the browser UI to handle login/session expiry and 401/404 responses.
6. Add cross-user authorization tests.
7. Run a deployment smoke test through the gateway.
8. Only then reconsider public access.

## Explicit non-goals

- Do not place a shared API secret in frontend JavaScript.
- Do not trust a user ID, email, or conversation owner sent by the browser.
- Do not treat CORS, an unguessable conversation ID, or a hidden URL as authentication.
- Do not claim the service is production-secure based on a successful health check.
